# TBG AI 评估实验室

## 2026-10-07 规则更新：华扇仅替代四卡阵营

华扇现在只能补足需要四张牌的阵营，不能与一张白玉楼、博丽、太阳花田或天界牌构成收取。实际规则、取牌估值、手牌材料、代价保留、商品交易与完成预测使用同一个阵营匹配判断。鵺借用该技能时也遵守这个限制。

评估中的当前、燐与觉更新前、历史策略均采用这一新规则；冻结策略仅适配华扇的匹配范围，没有调整其策略权重。导出使用新的规则与策略摘要，`currentPolicy` 为 `retrieval-and-trade-guard-kasen-four-2026-10-07`。**这批结果不能与削弱前的对局合并统计。** 版本对战仍检验相同规则下的策略差异，不能单靠它判断本次削弱对阵营平衡的影响。重新评估时请另用一个种子，例如 `TBG-kasen-four-2026-10-07`。

## 2026-10-07 更新：燐、觉与紫的交易保护

默认对照为 **燐与觉更新前的 AI**（`previous`），来源于提交 `955c63140738e5cc9deae85802cec12f10c5d61a`。它保留此前的神奈子、荷取、赫卡提亚、紫和隐岐奈策略；这项对照检验新增的燐、觉评估与紫的交易保护。早期 `2b07010…` 策略仍可选，界面名称改为 **历史 AI（早期版本）**（`baseline`）。不要把这两种对照的结果混为一批。

燐会比较拿到的卡能否完成阵营、其手牌材料价值、移走对手弃牌的实际分数，以及拿回自己弃牌的分数损失。不会无条件优先贤者牌，也不会把减少对手分数算成自己立即获胜的分数。觉在查看前只依据公开牌、已知线索与手牌张数估计可取牌的收益，并扣除支付卡的价值；查看后再按实际候选牌选择。查看前的未知手牌估计采用均匀、不放回的抽样假设，这仍是有限的启发式，不能保证最优。

当前策略的所有难度均禁止用八云紫报价，包括普通交易、为神奈子购牌和为两卡阵营购牌。执行交易时也有检查。人类玩家依然可以交易紫；旧策略与“关闭紫的交易保护”对照允许这个旧行为，以便验证差异。

推荐先固定 **200 开局组、三人、Hard、两种棋盘、本次修改前的 AI、新种子 `TBG-retrieval-check-2026-10-07`**。共 1200 局，每个座位公平轮换。整批完成后导出 **JSON 与 CSV**。进一步定位贡献时，可分别选择“关闭燐的新评估”“关闭觉的新评估”“关闭紫的交易保护”，其他设置保持一致。用未看过的种子做最终验证；小幅胜率变化需要连同按开局组计算的误差区间判断。

新增记录如下。实际变动与预测明确分开；实际胜负仍是评估强弱的主要依据。

| 字段 | 可回答的问题 |
|---|---|
| `card_actions` | 技能实际获得多少手牌、窃取多少牌、丢失自身多少分、支付多少牌，以及每张牌被作为代价或交易出去多少次？ |
| `ability_details` | 隐岐奈或鵺复制某技能时，由谁使用、是否生效、实际付出多少代价？ |
| `score_sources` | 分数来自阵营收取还是具体技能，哪些弃牌分数后来被移走？ |
| `diagnostics.costByAbility` | 每个使用者与技能付掉了哪些牌，支付后有多少次使已凑足数量的阵营材料不足？ |
| `diagnostics.tradePairs` | 哪张牌被换成了哪张牌，是否有紫被交易掉？ |
| `diagnostics.retrievals` | 燐与觉具体取得哪些卡、来自哪个席位、移走多少对手分数、损失多少自身分数？ |
| `diagnostics.skips` | 哪些代价技能被主动跳过了多少次？ |
| `diagnostics.yukariTradeGuardTurns` | 持有紫且规则允许交易时，有多少个实际行动决策应用了保护？这不是“差点错误交易”的次数。 |
| `diagnostics.events` | 每个席位最近 16 条行动、代价、取牌选择、跳过原因与结算记录。`omittedEvents` 标明更早省略的记录数。累计计数与卡牌明细不受这个上限影响。 |
| CSV 追加的配置与哈希字段 | 本批的主种子、开发/验证组、难度、对照策略、逐局种子以及规则/策略版本是否一致？ |

`forecast` 是预测，`ability-result` 是实际结算；预测中的 `matchesChosenCell` 为假时，表示它记录的是该牌的最佳估计位置，而实际选择了另一个位置。拿回自己弃牌产生的分数损失单独记录。`costAssemblyBreaks` 仅说明支付使阵营材料数量不足，不证明这次支付一定错误，也不证明之前一定能完成连接。一次实际决策可能产生多种技能或额外行动，不能把决策次数直接当作普通回合数。`handGained` 包含从弃牌、对手手牌及抽牌堆得到的牌，且不含付掉的牌；它不是净手牌变化。

导出保持原 CSV 前 17 列顺序，在后面追加数据。JSON 使用紧凑格式减少文件大小。中途进度只传新完成的开局组，最终文件仍包含全部已完成记录。普通纯电脑测试也保留新增实际卡牌计数与累计决策统计；逐局、逐策略比较应使用评估实验室。

命令行同样会输出 JSON 和同名 CSV，无需第三方依赖：

```bash
node tools/evaluate-ai.cjs --blocks 200 --players 3 --size both --opponent previous --difficulty hard --phase holdout --seed TBG-retrieval-check-2026-10-07 --out reports/retrieval-check.json
```

这次回归检查验证了新取牌选择、支付与预测一致、不偷看未知手牌、永琳禁用、借用技能归属、所有交易入口、各难度和导出。修改前的策略还与原文件的固定种子对局逐项比较，确认结果、回合、使用与收取记录一致。少量真实引擎对局仅用于检查运行与卡牌守恒，不能代替你的大批强度评估。

入口在主菜单折叠的 **Debug tools → AI 评估实验室**。游戏中也可从 Debug tools 打开。所有模拟在独立后台 Worker 中运行，不改变当前对局的牌堆、手牌或随机数。

## 先做版本对战

1. 选择“旧版 AI”，三人、Hard、两种棋盘。
2. 开局组数可以先用默认的 40 组，共 240 局。种子、规则、人数和棋盘配置相同，才能比较不同测试。
3. 开始后等待整批完成，导出 JSON 和 CSV。可以暂停、继续或停止；停止时只比较已经完整跑完的开局组。
4. 调整策略时使用开发组。策略确定后，再用保留验证组；如果看过验证结果并据此调整策略，下一次验证应使用新的种子。

接下来一批较大的测试建议预先固定 **200 组、三人、Hard、两种棋盘、保留验证组、新种子 `TBG-confirm-2026-10-07`**，共 1200 局。等整批结束再判断，避免看到好结果就提前停止。局数本身不保证结论；误差区间仍可能包含零。

旧策略来自提交 `2b07010618c21eee6dfc6ffd4092c8b4bbb42e9b`，保留独立的评估、交易、代价选择和技能目标选择。小町的额外行动预估适配了当前规则。当前策略来自 `59a9e6c9bf35941d19a957b3eb250acd9b766c1c` 的阵营 AI 改动。**两者始终共用同一个 Game 规则引擎**，因此这项比较检验策略收益，不把小町的规则加强混入策略差异。

每组固定起手、牌堆、香霖堂商品和规则随机种子，测试所有混合座位组合。两人每组 2 局，三人 6 局，四人 14 局。每个座位使用两种策略的次数完全相等。4×4、5×5 交替使用。规则随机流与 AI 决策随机流分开；两种策略做出不同动作后，事件与随机数的对应关系仍可能不同。

## 怎样读结果

- **比赛得分率**：正常获胜记 1；僵局由最高分玩家得 1，并列时平分。除以该策略参与的玩家局数。三人对称条件下参考值为三分之一。
- **胜率**：只计算正常达到获胜条件的对局，不把僵局计为正常胜利。
- **差异和 95% 误差区间**：以完整开局组为单位进行 1600 次成组 bootstrap 重采样，保留同开局、不同座位对局之间的关联。它描述本测试分布下的抽样不确定性。
- **运行错误或 600 回合超限**：保留诊断，并排除该对局所在的完整开局组。不要把这些情况偷偷计成平局；排除比例较高时，应先分析其原因。
- **结论**：预定批次结束且至少 20 个完整开局组时才给出方向判断。区间包含零时显示“暂时无法确认差异”。20 组只是最低报告门槛，并非充分证明。
- **阵营收取率**：该策略的玩家对局里，收取过该阵营的比例。
- **卡牌使用率**：收到过该牌的玩家对局中，至少放置过一次的比例。
- **持牌回合数**：该牌在其拥有者回合开始时仍在手中的累计次数，包括额外回合。总数会受到收到该牌的次数和对局长度影响，应结合使用率分析。

指标来自实际卡牌变动和对局结果，不使用 AI 自己的评分来宣布其判断正确。阵营收取率和使用率用于解释行为，最终是否更强仍应参考比赛结果及其不确定性。

## 逐项验证战略假说

“对照策略”还提供六个开关，与完整当前 AI 对战：

| 对照策略 | 被关闭的部分 |
|---|---|
| 关闭代价保牌策略 | 新增的主动跳过代价技能和保护凑牌材料的判断 |
| 关闭神奈子收尾策略 | 神奈子的新增评估，改用旧评估 |
| 关闭荷取铺场评分 | 荷取的新增铺场收益与对应排序优待 |
| 关闭赫卡提亚铺场评分 | 赫卡提亚的新增铺场收益与对应排序优待 |
| 关闭紫的新评估 | 紫使用旧评估 |
| 关闭隐岐奈的新评估 | 隐岐奈使用旧评估及旧的复制来源选择 |

这些开关不改变卡牌规则。其他当前策略继续保留，所以能检验一个组件在整套当前策略里的贡献。组件之间可能相互依赖；单项收益不应直接相加。测试许多版本后挑出的好结果，需要在未用过的开局上重新验证。

## 比较自己与 AI 的具体选择

1. 在实际对局里，遇到值得研究的选择时打开实验室，展开“局面分叉”。
2. 点击“使用最近回合局面”。保存的是最近一个普通回合开始、尚未行动的完整状态，包含行动限制、强制放置、已借用能力和待执行额外行动。不会截取正在进行的技能或额外回合连锁。
3. 选择行动 A、B：可比较合法放置、普通抽牌或交易。也允许 AI 策略通常会回避的合法放置。技能目标和代价由后续 AI 决定，这里不逐项指定技能选择。
4. 默认分别用当前、旧版两种策略继续，每种 20 次成对试验。A、B 的每一对使用相同的隐藏牌抽样和规则种子。推荐动作仅作选择参考。
5. 查看两种后续策略的结果是否一致，导出 JSON / CSV；局面也可单独保存、导入。

未知对手手牌与牌堆顺序会重新抽样，保留行动者已知的卡牌和公开的强制放置指令。交换真实未知手牌的分配不会改变抽样结果。行动者的手牌、公开棋盘和弃牌保持原样。对手的私有线索记忆未建模。之后所有座位由选定 AI 控制。

因此分叉结果是“在这些信息假设和后续策略下，哪个首步更有利”的估计，不能证明绝对最优。换一个局面或对手，答案可能改变。

策略固定后进行了两批各 20 组、120 局的三人 Hard 测试。种子为 `TBG-pilot-2026-10-06`，开发和保留验证使用不同的种子命名空间，起手与牌堆相互独立。每批各有 180 个当前策略玩家局和 180 个旧策略玩家局。

| 批次 | 当前比赛得分率 | 旧版比赛得分率 | 差异 | 差异的 95% 区间 | 结论 |

## 用 Node 运行相同引擎

无需安装第三方依赖。在仓库根目录运行：

```bash
node tools/evaluate-ai.cjs --blocks 200 --players 3 --size both --opponent baseline --phase holdout --seed TBG-confirm-2026-10-07 --out reports/confirmation.json
```

用导出的评估 JSON 重复同一配置（局面分叉会同时读取其中的局面）：

```bash
node tools/evaluate-ai.cjs --request reports/ai-comparison-pilot-2026-10-06.json --out reports/repeated-pilot.json
```

复现比较配置时看逐局结果，不比较时间戳。CSV 的首列说明对战或分叉；分叉保留试验种子、后续策略与 A/B 标记。两种运行方式从 HTML 提取相同规则和 AI，并执行真实的回合、交易、技能和额外回合处理。
